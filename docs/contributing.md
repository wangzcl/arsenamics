# 参与本项目

欢迎参与本项目！无论你是否熟悉为开源项目贡献内容的流程，我们都欢迎你的参与。即使你不熟悉你打算介绍的工具，也可以在参与项目中边实践边学习。新手的经验体会可能反而比专业人士更宝贵。

## 给本项目写文章

我们已经搭建好了一个基于 [Material for MkDocs](https://squidfunk.github.io/mkdocs-material/) 的文档框架。基本上，你只需要关注内容，编辑 Markdown 文件即可（可能还有 `.nav.yml` 目录文件）。

我们尽自己所能来简化参与开发的流程。如果只进行常规编辑，比如添加一个文件或修改现有文件的文本，所有操作在 GitHub 网页端就可以完成，但是这样无法即时预览生成的网页效果，Git 版本控制功能也受限。请参考 [在线编辑](#在线编辑)

如果你想在本地开发，预览生成的网页是什么效果，以及进行更细的版本控制，请参考[本地编辑](#本地编辑)。

无论你采用哪种编辑方式，请参考 [Contributing to a project - GitHub Docs](https://docs.github.com/en/get-started/exploring-projects-on-github/contributing-to-a-project) 了解如何用 Git 和 GitHub 上进行协作。我们也会在本项目中介绍相关工具的使用（开发中）。

### 在线编辑

1. 登录你的 GitHub 账号，找到本项目的 GitHub 网页，点击右上角的 Fork 按钮，将本项目 Fork 到你的 GitHub 账号下。这会创建一个本项目的副本，你可以独立地在其中进行修改，并将改动提交给原项目。
2. 进入你 Fork 的 GitHub 页面，点击文件列表左上角的分支选项下拉菜单（现在上面应该是 `main`，因为你默认在 `main` 分支），新建一个临时的开发分支，可以起名叫 `dev` 或者根据你打算写的内容起其他名字，然后切换到 `dev` 分支。现在 `dev` 和 `main` 版本完全一致，但是如果你更新了 `dev`，`main` 不会受影响。请一定在专门的开发分支上进行开发，`main` 分支只用来和项目的主仓库作同步用。
3. 现在你可以直接在网页上添加和编辑 Markdown 文件了。注意：Material for MkDocs 包含一些 Markdown 扩展语法，可能在 GitHub 上无法正确显示。请参考[编辑指南](#编辑指南)和[内容清单](#内容清单)。
4. 提交（commit）你的编辑，来更新你的你的 `dev` 分支。一个提交应该只包含一个完整、自洽的修改， 例如修复一个错误或者添加一个新工具的介绍。提交时，在 commit message 中使用极简的英文描述你所做的修改， 如“ADD vscode intro”。你可以多次提交，但是 GitHub 网页端的版本控制不太灵活，所以请谨慎操作。
5. 提交后，紧挨着文件列表上方的地方，你的头像旁边会显示你的 commit message，以及一个符号（可能是棕色的点，叉号或勾），这意味着我们设置的 GitHub Actions 正在自动检查你的新版本能否正确生成网页。如果 GitHub Actions 运行失败，请检查报错情况，并继续修改提交来修复错误。
6. 完成编辑后，给我们发一个 Pull Request (PR)，请求管理员把你在你的 `dev` 分支里所做的改动合并到我们的主仓库 `main` 分支里。如果你的开发分支里有多个提交（更新了几个版本），你也可以只 PR 某一个老版本。请在 Pull Request 的描述中简要说明你所做的修改。请尽可能确保一个 PR 完整、自洽，只做一件事。
7. 如果你的修改被接受了，请删除你的 `dev` 分支，并将你 Fork 的 `main` 分支同步到主项目的最新版本。之后，你可以创建新的开发分支，继续为本项目贡献内容。

### 本地编辑

1. 确保你安装了 Git 和 Git LFS。
2. 在 GitHub 上 Fork 本项目（参见[在线编辑](#在线编辑)）
3. 在你的计算机上， 使用 `git clone <url>` 来克隆你的 Fork（即将其下载为一个本地文件夹， 该文件夹关联到你在 GitHub 上的 Fork）。
4. 在你本地项目文件夹创建一个新的开发分支，参见（参见[在线编辑](#在线编辑)）
5. 如果你需要在本地预览生成的网页是什么效果，则需要一个 Python 环境，在其中安装 MkDocs 等相关软件包。另外，我们使用 `pre-commit` 来在提交前自动规范 markdown 文件格式。如果你不熟悉如何配置 Python 开发环境，我们建议使用 [uv](https://docs.astral.sh/uv/) 管理项目所需要的依赖项，步骤如下：
    1. [安装 uv](https://docs.astral.sh/uv/getting-started/installation/) 。
    2. 在项目根目录下运行 `uv python install` 安装一个由 uv 管理的 Python， 版本与本项目要求的 Python 版本一致。
    3. 运行 `uv sync` 来安装项目的 Python 依赖项 (如 `mkdocs-material`)。这会在项目根目录下创建一个 `.venv` 文件夹， 里面是一个独立的 Python 虚拟环境，自动安装了本项目所需的所有 Python 依赖项。
    4. 运行 `uvx pre-commit install` 来安装 `pre-commit` 工具。这个工具的功能是，每当你使用 `git commit` 提交代码时，自动检查你修改的文件是否符合项目的格式要求，自动修复一些常见的格式问题。
    5. 运行 `uv run mkdocs serve` 来启动一个本地的 MkDocs 服务器。终端里会显示一个网址，在浏览器里打开这个网址，就可以看到本项目的网页了。你在本地修改 markdown 文件并保存后，更新通常实时反映在网页上。
6. 编辑、提交和 PR 和[在线编辑](#在线编辑)类似，但是需要在本地和云端之间手动同步。请参考[编辑指南](#编辑指南)和[内容清单](#内容清单)来撰写文章。

### 编辑指南

所有的文档都必须放在在 `docs/` 文件夹里。你可以按实际需要来修改、添加其中的 markdown 文件和文件夹。注意以下几点：

- 用简洁的英文来命名文件和文件夹。请勿使用中文字符、空格或其他特殊字符。需要使用空格时，替换为连字符（`-`）。这是因为文件结构决定了网页的 URL 地址。
- 建议采用扁平的文件结构，减少文件夹深度，方便管理。
- MkDocs 默认使用 markdown 文件的一级标题（`#`）作为网页的标题，以及页面左边导航栏中显示的内容。
- 导航栏会根据文件结构自动生成，但是这会造成一些问题：它会使用文件夹的英文名称，并且可能弄乱 markdown 文件的顺序。为了避免这些问题，我们使用 [Awesome Nav for MkDocs](https://lukasgeiter.github.io/mkdocs-awesome-nav/) 插件， 在 `.nav.yml`文件中 手动配置导航栏。假设你创建了一个新的文件夹 `docs/foo/`，添加了两个 markdown 文件 `docs/foo/bar.md` 和 `docs/foo/baz.md`，你可以在 `docs/.nav.yml` 文件中合适的地方插入以下内容：

    ```yaml title="docs/.nav.yml"
    - foo 在导航栏中的显示名称: foo
    ```

    再新建一个 `docs/foo/.nav.yml` 文件来配置 markdown 文件在导航栏中的显示顺序：

    ```yaml title="docs/foo/.nav.yml"
    - bar.md
    - baz.md
    ```

    需要更多信息，请参考 Awesome Nav for MkDocs 的文档。
- 如果要在 markdown 文件中插入图片，请将图片放在 `docs/assets/images/` 文件夹下。
- 需要使用高级语法（如注释、代码块），请参考 [Material for MkDocs 官方参考文档](https://squidfunk.github.io/mkdocs-material/reference/)。

### 内容清单

1. 需要哪些工具？为什么需要这些工具？
2. 工具的选择：关注最佳实践。注重通用性：工具应该有超出单一领域的意义；注重简洁性：平衡工具学习和工具运用之间的时间
3. 所介绍工具的功能和优劣
4. 用尽可能通俗的语言介绍工具背后的基本逻辑、理念、概念，方便快速入门
5. 介绍常见陷阱和误区
6. 列出该工具的参考资料链接，方便进一步探索。读者在阅读完本教程后应该具备理解参考资料的能力
7. 工具之间如何交互和集成
8. 使用这些工具的典型日常工作流是怎样的？模拟真实情境的教程
